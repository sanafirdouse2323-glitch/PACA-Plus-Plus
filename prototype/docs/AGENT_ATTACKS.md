# Agent attack boundary: enforce policy outside the model

For retrieval-time provenance filtering and output exfiltration checks, see [Content boundaries](CONTENT_BOUNDARIES.md). `GuardedAgentPipeline` composes the existing tool-call, retrieval and output gates without reimplementing authorization; the host LLM orchestrator must use it for every relevant path.

## Purpose and scope

This is an initial executable guard at the tool/effect boundary for LLM-agent systems. It does not try to prove that a model can never be prompt-injected. Instead, it prevents model-generated text from directly choosing arbitrary action names, resource IDs, routes, or argument fields, and ensures each proposed action still goes through the existing guarded gateway.

Prompt injection can arrive in user messages, retrieved documents, web pages, memory, or tool responses. The words in those sources are not authorization. Never derive allowlists, policy, credentials, action/resource routing, or approval from them.

## Controls implemented

- Static tool allowlist. Each model-visible tool name maps to a fixed server-configured action and resource.
- Exact top-level shape and strict flat argument schema. Unknown fields, missing required fields, invalid types, range violations, non-finite numbers, non-JSON values, invalid Unicode, and oversized/deep payloads are rejected before tool execution.
- Per-tool argument size, total run argument size, per-run call count, and returned-result size limits.
- Request digest and call-ID binding. Repeating the same completed call ID returns a copy of its cached result without executing a second effect; rebinding that ID to different arguments is denied. A failed/in-flight call is not automatically replayed.
- Optional high-impact approval gate. Such tools fail closed unless a configured verifier accepts a token bound to the trusted approval subject, exact tool/action/resource, and canonical argument digest. The verifier must check expiration and one-time use against an independently trusted approval record. No approval issuer or user interface is included here; do not let the model generate its own approval.
- Tool outputs are wrapped as AgentToolResult with trust set to untrusted_tool_output. That label does not sanitize the payload or make the model ignore hostile text. The caller must preserve the trust label and route every subsequent tool proposal through the same boundary.
- Audit callbacks receive event names, call IDs, tool names, request hashes, and reason codes, not raw arguments, credentials, approval tokens, or tool outputs.
- Execution is delegated to an injected executor. The provided ticket helper binds the tool to the existing GuardedGateway, which performs identity, trusted-context, OPA, durable permit, and fixed-adapter checks.

## Example: bind the ticket tool to GuardedGateway

Run from the prototype directory after installing the package. The credential must come from the authenticated caller, the adapter and gateway must be constructed from trusted configuration, and operation_id must be generated by the orchestrator rather than by the model.

~~~python
from paca_mvp import build_ticket_create_boundary

boundary = build_ticket_create_boundary(
    gateway=guarded_gateway,
    credential=verified_callers_access_token,
    adapter=ticket_adapter,
)

result = boundary.invoke(
    {"tool": "ticket_create", "arguments": {
        "title": "Unexpected agent action",
        "description": "Created through a policy-guarded tool boundary.",
    }},
    call_id=trusted_operation_id,
)

# Treat result.payload as untrusted data even when the tool call was authorized.
print(result.trust)  # untrusted_tool_output
~~~

The ticket helper exposes only ticket creation. It does not grant the agent a generic HTTP client, shell, filesystem, or arbitrary URL capability. Add a new ToolSpec only after defining the exact action/resource mapping and validated argument schema. For high-impact tools, set requires_approval=True and provide an approval_verifier whose approval state is obtained outside the model process.

## Limits and deployment requirements

- This does not detect every prompt injection. It enforces authorization and input constraints even when prompt injection succeeds in influencing the model.
- The call cache is in-memory and scoped to one boundary instance/run. It is not a durable distributed idempotency store. Keep the existing durable GuardedGateway store and downstream idempotency/reconciliation contracts for protected effects.
- A process crash can discard the local call cache. Remote effects can have unknown outcomes; reconcile before retry. A tool-specific downstream idempotency implementation is still required.
- The boundary is not a sandbox for executor code and does not prevent a separately reachable tool endpoint from being called directly. Every sensitive effect must be reachable only through the guarded gateway, or independently enforce equivalent authorization.
- Returned content remains untrusted. Do not execute instructions embedded in output, merge it into policy/configuration, or accept it as approval. Use separate identity and policy channels and require explicit approval for destructive or externally visible actions.
- Default budgets are generic example values; choose deployment-specific limits and rate limits. Human approval should bind the approving principal, action, resource, exact arguments, expiry, and a one-use nonce in a trusted service.
- No claim is made that this change makes all AI agents safe, blocks all prompt injection, provides formal proof, or is production-ready without integration review, end-to-end tests, and independent security assessment.

## Tests

The adversarial tests cover injection text that attempts to change routing, unknown tools/fields, type and size violations, approval binding, replay/rebinding, call budgets, result limits, output taint labelling, and gateway integration. Run all prototype tests with:

~~~bash
cd prototype
python -m pip install -e ".[web,test]"
python -m unittest discover -s tests -v
~~~
