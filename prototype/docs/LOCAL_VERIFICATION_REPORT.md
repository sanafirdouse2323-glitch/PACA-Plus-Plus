# Verification report and reproducibility instructions

This document describes how to reproduce verification. It is not a live dashboard: always check GitHub Actions for the exact commit SHA being evaluated.

## Verification layers

- **Root compiler tests:** run `PYTHONPATH=. python -m unittest discover -s tests -p "test_fuzzer.py" -v` from repository root. These test the supported parser/emitter subset only.
- **Legacy prototype:** run `python -m unittest discover -s tests -v`, `python examples/demo.py`, and `python experiments/run_experiments.py` from `prototype/`.
- **Production service:** run `pytest -q` and `ruff check .` from `production_service/`; database-specific tests require a restricted runtime DSN and a separate admin DSN for fixture/schema setup.
- **CI:** [open the repository Actions history](https://github.com/sanafirdouse2323-glitch/PACA-Plus-Plus/actions) and confirm required workflows passed on the exact candidate commit. A green run on another SHA or branch does not verify this revision.

## Scenario result artifact

`prototype/experiments/results.json` is generated by `prototype/experiments/run_experiments.py`. The prototype workflow reruns the runner and fails if it changes the checked-in result file. If the runner or scenarios change, review and commit the regenerated artifact intentionally.

## Limits

All hand-authored tests cover specific scenarios only. They are not an external benchmark, independent security audit, formal proof, standards-conformance evidence, production-readiness approval, or proof of research novelty. Real downstream behavior, OIDC configuration/key rotation, failure/recovery handling, operational controls, and deployment security require separate evaluation.
